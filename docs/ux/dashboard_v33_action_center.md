# Dashboard v3.3 — Action Center (концепция, rev. 2)

**Статус:** концепция на согласование (rev. 2 — правки владельца внесены). Код не пишется до финального утверждения.
**Цель:** превратить Dashboard из аналитической панели в рабочий инструмент владельца магазина: «что сломано / что требует действий — прямо сейчас».
**Ограничения:** только существующие данные backend; без изменений API; без изменений backend; только presentation layer.

---

## 1. Проблема, которую решаем

В v3.2 Dashboard отвечает на вопрос **«как идут дела?»** (деньги, выручка, тренды), но плохо отвечает на вопрос **«что мне сейчас нужно сделать?»**:

1. **Два разрозненных блока внимания** — Top Alert (баннер одной проблемы) и AttentionSection (сетка плиток-счётчиков). Владелец видит «5 out of stock» и «2 low on stock» как отдельные плитки без приоритета и без рекомендации.
2. **Нет ранжирования.** Критическая проблема (расхождение кассы) и мелкая (нет продаж сегодня) показаны одинаково весомо.
3. **Нет рекомендаций и переходов.** Плитка говорит «3 low on stock», но не предлагает действие («Создать заказ поставщику») и не ведёт в нужный раздел.
4. **Нет единого «All clear».** Когда всё хорошо, сетка исчезает бесследно — владелец не понимает, проверено ли.

**Решение:** один блок **«Requires Attention»** — единый приоритизированный список реальных бизнес-событий, где каждая строка = событие + причина + рекомендация + CTA-переход. Заменяет и Top Alert, и AttentionSection.

---

## 2. Концепция

**Action Center** — единственный блок внимания на Dashboard, расположенный сразу под Hero Cash Drawer.

### Правила

- **Три категории вместо четырёх уровней:** события делятся на **Critical** (красный), **Attention** (оранжевый/жёлтый) и **Opportunities** (синий/нейтральный-info). Сортировка: Critical → Attention → Opportunities; внутри категории — по весу (сумма расхождения, число позиций, % падения).
- **Одно событие = одна строка.** Каждая строка: иконка + цвет категории, заголовок события, **проблема**, **причина**, **рекомендация**, **оценка влияния на бизнес** (где вычислима), кнопка CTA (куда перейти).
- **Лимит видимости:** по умолчанию показываются первые **3** события; при большем количестве — кнопка **«Show all (N)»** (разворачивает список). Это сохраняет 5-секундную читаемость.
- **«All clear» — полноценное позитивное состояние** (см. §5): «Everything looks good», «No urgent actions», «Last checked X min ago».
- **Автообновление:** блок читает те же провайдеры, что уже живут на Dashboard (см. §4), и обновляется вместе с ними (таймер 20с + refresh при возврате на экран, как в Hero). Никаких новых фоновых опросов.
- **Loading / Error:** общий скелетон-стейт и компактный Retry — единые со стилем Hero.

## 3. Каталог событий (только существующие данные)

Все события построены строго на полях, которые реально возвращают текущие эндпоинты (проверено по коду backend и клиента). Для каждого события указаны: **проблема** (что видит владелец), **причина** (почему это происходит), **рекомендуемое действие**, **влияние на бизнес** (оценка там, где вычислима из уже доступных данных).

### 🔴 CRITICAL — деньги и продажи под угрозой

#### 1. Расхождение кассы (Drawer difference)
- **Проблема:** физическая касса не сходится с ожидаемым закрытием смены. `|difference| > 0.005` при открытой смене.
- **Причина:** ошибка пересчёта, неверная сдача, неучтённый cash in/out, ошибка кассира.
- **Рекомендация:** «Пересчитай наличные: ожидаемое закрытие **$Y**. Сверь движения и закрой смену.»
- **Влияние на бизнес:** расхождение = **прямые потери/излишек кассы $X уже сейчас** (сумма показывается). При повторении — системная проблема с деньгами, требует сверки ежедневно.
- **Источник:** `cashShiftProvider.current.difference` (X-report, уже грузится Hero).
- **CTA:** POS `saleNew` / Reports `reports`.

#### 2. Товары закончились (Out of stock)
- **Проблема:** **N** товаров с нулевым остатком — покупатель не может их купить.
- **Причина:** не пополнили вовремя; заказ поставщику не создан или ещё в пути.
- **Рекомендация:** «Пополни до того, как потеряешь продажу. Создай заказ поставщику сейчас.»
- **Влияние на бизнес:** каждая позиция out of stock = **потерянная продажа**. Оценка: **N × средний чек** потенциальной недополученной выручки за день (средний чек берётся из `/reports/dashboard` — `ordersCount` и `todaySales.revenue`; если данных мало — без численной оценки, только «риск потери продаж»).
- **Источник:** `/reports/dashboard` → `outOfStockProducts` или `/reports/inventory/low-stock` → items `OUT_OF_STOCK`.
- **CTA:** Products `products` / Purchasing `purchasing`.

### 🟠 ATTENTION — требует действий, но не критично прямо сейчас

#### 3. Низкие остатки (Low stock)
- **Проблема:** **N** товаров ниже порога остатка — скоро закончатся.
- **Причина:** уровень заказа не настроен/не соблюдается; поставки не планируются заранее.
- **Рекомендация:** «Закажи у поставщика, пока не закончились.»
- **Влияние на бизнес:** если не пополнить — **перейдут в out of stock за дни/неделю** (риск тех же потерянных продаж, что в событии 2). Детализация: список до 3 позиций с SKU и остатком.
- **Источник:** `/reports/dashboard` → `lowStockProducts` + `/reports/inventory/low-stock` → items `LOW_STOCK` (детализация).
- **CTA:** Inventory `inventory`.

**Этап B — детализация Low Stock (утверждено владельцем):**

- **Формат:** вместо абстрактного «5 low-stock products» показываются **top-3** наиболее критичных товара: название, SKU, текущий остаток, minimum quantity, склад, статус. CTA → существующий экран Inventory/Warehouse (`RouteNames.inventory`).
- **Правило сортировки (детерминированное и объяснимое):** товары сортируются по **дефициту** `deficit = minQuantity − currentStock` **по убыванию** (наибольший дефицит — первым); при равенстве — по названию товара (asc), затем по SKU (asc). Дефицит считается только для позиций `status == 'LOW_STOCK'` (позиции `OUT_OF_STOCK` обрабатываются событием 2).
- **Ограничение:** показываются **не более 3** позиций; остальные скрыты за «…и ещё N».
- **Поведение при 0 / Loading / Error:** если список low-stock пуст или не загрузился (Loading/Error), событие либо не показывается (0), либо показывается без детализации — **без ложных позиций и без выдуманных цифр**.
- **Источник данных:** 1 дополнительный лёгкий запрос `GET /reports/inventory/low-stock?limit=50` в `Future.wait` при initial load / manual refresh Dashboard (по образцу Decision события 4; на Hero timer 20с **не** выполняется). Модель `LowStockItem` в `dashboard_models.dart`, поле `DashboardData.lowStockItems`.
- **Формула дефицита и правило top-3 реализованы как чистые функции** `sortLowStockByDeficit()` / `lowStockDetailLines()` — unit-тестируемые.

#### 4. Заказы поставщиков ждут действий (Pending purchase orders)
- **Проблема:** **N** заказов поставщикам в статусе PENDING или ORDERED без движения.
- **Причина:** PENDING — не подтверждён менеджером; ORDERED — поставка не оприходована (Goods Receipt не сделан).
- **Рекомендация:** «PENDING — подтверди заказ; ORDERED — оприходуй поставку.»
- **Влияние на бизнес:** задержка поставки → **задержка пополнения склада → рост out of stock** (связано с событиями 2–3). Сумма в деньгах: сумма открытых PO (есть в данных `/reports/purchasing`).
- **Источник:** `/reports/purchasing` → `summary.byStatus.PENDING / ORDERED` (уже грузится виджетом Pending PO).
- **CTA:** Purchasing `purchasing`.

#### 5. Нет открытой смены (No open shift)
- **Проблема:** касса не готова принимать продажи — смена не открыта.
- **Причина:** кассир забыл открыть смену в начале дня.
- **Рекомендация:** «Открой смену, чтобы принимать продажи.»
- **Влияние на бизнес:** **прямая потеря выручки** — каждая минута простоя POS без смены = недополученные продажи (оценка: **минуты × средний чек/минута** по статистике вчерашнего дня; при отсутствии данных — без числа).
- **Источник:** `cashShiftProvider.current == null` (при наличии складов).
- **CTA:** POS `saleNew`.

#### 6. Смена открыта подозрительно долго (Shift open > 12h)
- **Проблема:** смена открыта **Hh ч**, дольше обычного.
- **Причина:** смену не закрыли в конце дня; кассир забыл/уволился/уехал.
- **Рекомендация:** «Возможно, стоит закрыть смену и сверить кассу.»
- **Влияние на бизнес:** усталость кассира → **ошибки в сдаче и пересчёте** (риск расхождений кассы); размытая ответственность за деньги.
- **Настройка:** порог **по умолчанию 12 часов**; в будущих настройках (Settings) значение станет конфигурируемым владельцем (см. §7). Пока — константа 12 ч.
- **Источник:** `cashShiftProvider.current.openedAt`.
- **CTA:** POS `saleNew`.

#### 7. Падение выручки vs вчера (Revenue drop)
- **Проблема:** выручка сегодня **−X%** относительно вчерашнего дня.
- **Причина:** сезонность/день недели, нет трафика, сломан витринный товар, промо конкурента — требует проверки владельцем.
- **Рекомендация:** «Посмотри динамику и причины снижения.»
- **Влияние на бизнес:** вычислимо напрямую: **−$Y недополученной выручки** относительно вчера (вчерашняя выручка − текущая; если сегодня не закончился — экстраполяция не делается, показывается только фактическая разница на текущий момент).
- **Источник:** `/reports/dashboard` → `todaySales.revenue` vs `yesterdaySales.revenue`.
- **CTA:** Reports `reports` (вкладка Sales).

#### 8. Ноль продаж сегодня при открытой смене (No sales yet)
- **Проблема:** смена открыта, а продаж сегодня ещё **0**.
- **Причина:** POS не готов (сканер/принтер), кассир не на месте, магазин закрыт по ошибке.
- **Рекомендация:** «Проверь готовность POS к продажам.»
- **Влияние на бизнес:** **0 выручки при открытой кассе** — простой торговой точки; показывается время с открытия смены («N ч без продаж»).
- **Источник:** `todaySales.count == 0` + смена открыта.
- **CTA:** POS `saleNew`.

### 🔵 OPPORTUNITIES — возможности роста / онбординг

#### 9. Нет складов (No warehouse yet)
- **Проблема:** компания не настроена — нет ни одного склада.
- **Причина:** онбординг не завершён.
- **Рекомендация:** «Сначала добавь склад — смены открываются по складам.»
- **Влияние на бизнес:** без склада **нельзя открыть смену и принимать продажи** (блокирует весь POS).
- **Источник:** `warehouseListProvider` (уже грузится Hero).
- **CTA:** Warehouses `warehouses`.

#### 10. Пустой каталог (Start building inventory)
- **Проблема:** стоимость склада $0 и каталог пуст.
- **Причина:** товары не созданы, остатки не заведены.
- **Рекомендация:** «Создай первые товары и заведи остатки.»
- **Влияние на бизнес:** **продавать нечего** — выручка невозможна до наполнения каталога.
- **Источник:** `/reports/dashboard` → `inventoryValue == 0` и товары пусты.
- **CTA:** Products `products`.

#### Событие 4 — семантика (утверждено владельцем)

- **Считаются «ожидающими действий» строго:** `PENDING` + `ORDERED`.
- **НЕ включаются** (зафиксировано для будущего review): `APPROVED` (подтверждён, но не отправлен поставщику) и `PARTIALLY_RECEIVED` (частично оприходован). В будущем эти два статуса могут быть добавлены в событие через единый enum-helper.
- `RECEIVED` / `CANCELLED` / `DRAFT` — терминальные/неактивные, никогда не смешиваются.
- При `count == 0` событие полностью исчезает; при Loading/Error ложное «0 orders» не показывается.
- CTA → существующий `RouteNames.purchasing`.

> **Исключено осознанно** (нет данных в текущих ответах без новых запросов/агрегаций): «высокая доля возвратов», «медленные продажи по товарам», «просроченные счета клиентов», «касса закрыта в рабочее время» (нет понятия «рабочего времени»). Эти события — кандидаты для **Future Events** (см. §8), в v3.3 их нет.

## 3a. Decision: Pending PO uses Dashboard-specific purchasing summary request

**Решение (утверждено владельцем, вариант C):** событие №4 использует **существующий** `GET /reports/purchasing` (мобильный эндпоинт уже объявлен в `ApiEndpoints.reportsPurchasing`, но ранее не вызывался).

**Причины:**

1. `poListProvider` **принадлежит экрану Purchasing** (его состояние мутируют search/filter/loadMore экрана).
2. Dashboard **не должен зависеть от того, посещал ли пользователь Purchasing** — блок внимания должен ловить то, что владелец ещё не видел.
3. `/reports/purchasing` **уже существует на backend** — новый endpoint не нужен.
4. Запрос **лёгкий** (`limit=1` — тянем только `summary.byStatus` через groupBy без пагинации) и выполняется **параллельно** с остальными dashboard-запросами через существующий `Future.wait` в `_fetchAll()`.
5. **Дополнительных запросов на Hero timer (20с) нет** — purchasing-запрос выполняется только при initial load / refresh Dashboard, а не на таймере автообновления Cash Drawer.

**Стоимость:** ровно **1** дополнительный запрос на каждую загрузку/обновление Dashboard (без добавочной задержки — параллельно).

### Decision: Low Stock detail uses existing /reports/inventory/low-stock

**Решение (Этап B):** событие №3 использует **существующий** `GET /reports/inventory/low-stock` (эндпоинт объявлен в `ApiEndpoints.reportsLowStock`). Причины: данные о конкретных позициях (SKU/остаток/склад) **не доступны** в `GET /reports/dashboard` (там только счётчики), а на Dashboard нет готового провайдера low-stock — запрос добавляется по образцу события 4: **1** лёгкий параллельный запрос при initial load / manual refresh, **не** на Hero timer 20с.

### Правила impact estimates (Этап B, утверждено владельцем)

1. **Численные значения показываются только если они непосредственно вычисляются из уже доступных данных** и формула прозрачна:
   - Drawer difference: фактическая разница кассы `|difference|` — уже отображается как есть;
   - Revenue behind yesterday: фактическая разница `yesterdaySales.revenue − todaySales.revenue` — уже отображается как есть;
   - Out of stock: средний чек используется **только как ориентир** и **обязательно помечается** — `≈ $X lost sales/day (estimate)`; без среднего чека — качественный текст `Risk of lost sales`.
2. **Где точного impact нет — качественный текст** (`Risk of lost sales`, `Delayed replenishment …`), а не выдуманный `$X lost`.
3. Не допускается финансовая оценка для событий, где данные не позволяют её вычислить (low stock — только качественно: риск stockout).

### Decision: Onboarding «N of 4» — семантика (Этап C, утверждено владельцем)

**Решение:** `N of 4` — это **прогресс завершённых onboarding-действий**, а не универсальный индикатор состояния бизнеса.

**Шаги (строго фиксированы):**

1. **Products** — done, если `hasStock`: `inventoryValue > 0` **или** `lowStockProducts > 0` **или** `outOfStockProducts > 0` (proxy из `/reports/dashboard`; принят, поскольку счётчика товаров в ответе нет, а договорённость — использовать только существующие данные).
2. **Customers** — done, если `customerCount > 0`.
3. **Open shift** — done, если `cashShiftProvider` в состоянии `ShiftLoaded` и `current != null` (открытая смена загружена).
4. **First sale** — done, если `ordersCount > 0` **или** `todaySales.count > 0`.

**Правила:**

- `Done` показывается **только** когда соответствующее условие реально выполнено. Никакого искусственного обеспечения достижимости `4/4`.
- Новые API/запросы **не добавляются** — шаги читают уже загруженные `dashboardProvider` и `cashShiftProvider` (оба и так живут на Dashboard).
- **Loading / Error** → скелетон героя, никакого ложного «0 of 4».
- Завершённые шаги не кликабельны (галочка + «Done»/«Completed»); незавершённые — «N» + «Get started» с CTA в существующие экраны (`productCreate`, `customerNew`, `saleNew`).
- Порядок шагов и условия зафиксированы; будущие изменения (например, явный счётчик товаров в `/reports/dashboard`) — отдельным решением.

## 4. Карта данных (без новых API)

Все 10 событий читают **уже загружаемые** на Dashboard данные:

| Провайдер / запрос | Что даёт Action Center |
|---|---|
| `dashboardProvider` (`GET /reports/dashboard`) | события 2, 7, 8, 10 (+ средний чек для оценок влияния 2, 5) |
| `cashShiftProvider` (`GET /sales/cash-shifts/x-report`) | события 1, 5, 6, 8 |
| `warehouseListProvider` (`GET /warehouses`) | событие 9 (и guard для 5) |
| `lowStockProvider` / виджет Low Stock (`GET /reports/inventory/low-stock`) | детализация событий 2–3 (список товаров, SKU, остаток) |
| `purchasingProvider` / виджет Pending PO (`GET /reports/purchasing`) | событие 4 (статусы и суммы PO) |

**Принцип:** Action Center — чистый потребитель (ConsumerWidget), как уже сделано с AttentionSection. Ни одного нового эндпоинта, ни одного дублирующего запроса.

**Вариант «All clear» (полноценное позитивное состояние):**

```
┌─ Requires Attention ─────────────────────────────────────────────────────┐
│                                                                          │
│  ✅  EVERYTHING LOOKS GOOD                                               │
│      No urgent actions.                                                  │
│      Last checked 3 min ago                                              │
│                                                                          │
│  [ Show opportunities (2) ▸ ]   ← необязательный раскрыватель,           │
│                                   показывает только Opportunities (9–10) │
└──────────────────────────────────────────────────────────────────────────┘
```

### Правила отрисовки

- Шапка: заголовок «Requires Attention» + бейдж количества (если > 3 — «N»).
- Строка события: цветовая полоса категории слева (🔴 Critical / 🟠 Attention / 🔵 Opportunities), заголовок жирным, строки «Проблема / Причина / Действие» компактно, строка «Влияние» — курсивом с денежной/количественной оценкой, CTA-кнопка справа (появляется и по hover, и статично для touch).
- Вложенная детализация (для событий 2–3): до 3 позиций списком с SKU — данные из low-stock items.
- **All clear** — полноценный позитивный блок: зелёная галочка, «Everything looks good», подзаголовок «No urgent actions», строка «Last checked X min ago» (механизм времени — тот же, что «Updated X sec ago» в Hero). При наличии только Opportunities — компактный раскрыватель «Show opportunities (N)».
- Мобильная версия: строки вертикальные, CTA — на всю ширину снизу строки.
- Анимации: появление строк каскадом (Fade+Slide 150ms), hover-подсветка, переход CTA — штатные маршруты через `context.push`.

## 7. Алгоритм приоритизации (детали)

1. **Сбор:** собрать сырые сигналы из провайдеров (§4).
2. **Категоризация:** каждый сигнал относится к одной из трёх категорий — Critical (1–2), Attention (3–8), Opportunities (9–10).
3. **Взвешивание внутри категории:**
   - Critical: |расхождение кассы| по убыванию → число out-of-stock позиций.
   - Attention: число low-stock → PENDING/ORDERED заказы → «нет смены» → «долгая смена» → % падения выручки → «ноль продаж».
   - Opportunities: онбординг-состояния (склад → каталог).
4. **Дедупликация:** «no open shift» и «shift open 14h» взаимоисключающие; события 7 и 8 могут сосуществовать (оба про продажи), но 8 показывается только если не показано 7 (чтобы не дублировать «про продажи» дважды).
5. **Отсечка:** максимум **6** событий в развёрнутом списке; остальное скрыто за «Show all» с точным счётчиком. Opportunities по умолчанию свёрнуты, если есть хотя бы одно Critical/Attention событие.

### Порог «долгой смены» (событие 6)

- **Сейчас:** константа **12 часов** в presentation layer (в коде — именованная константа с комментарием).
- **Будущее:** значение станет настройкой владельца в разделе Settings (UI-only, без backend) — «долгая смена, ч» с дефолтом 12. В v3.3 константа выносится так, чтобы будущая настройка подключалась заменой одного источника значения.
