# v1.1.1 — Accounting Consistency Patch: Audit & Validation Report

**Date:** 2026-08-05
**Scope:** Close the two accounting inconsistencies found by the v1.1 cross-module production audit.
**Constraint:** Reporting/minimal patch only — no schema changes, no API changes, no Flutter changes, no costing-engine or GL-engine redesign.

---

## 1. Root cause summary

### Fix #1 (Critical) — Negative inventory adjustments posted an inverted journal entry

`backend/src/modules/inventory/events/finance-integration.handler.ts` posted **the same journal direction for increases and decreases**:

```
Before (bug):
  Increase:  Dr Inventory (1300) / Cr Adjustment (5100)   ✅
  Decrease:  Dr Inventory (1300) / Cr Adjustment (5100)   ❌ inverted

After (fix):
  Increase:  Dr Inventory (1300) / Cr Adjustment (5100)   ✅ unchanged
  Decrease:  Dr Adjustment (5100) / Cr Inventory (1300)   ✅ corrected
```

The `isIncrease ? … : …` ternaries swapped the *account ids* but not the *debit/credit positions*, so every decrease posted `Dr 1300 / Cr 5100`, inflating GL Inventory and deflating the adjustment account. The trial balance stayed balanced (masking the defect), but the required invariant **GL Inventory == Inventory Valuation** silently failed on every negative adjustment (write-off, count-down, damage).

### Fix #2 (Medium) — Refunds were not netted out of the active Cash Shift

`refundSale` only published `SaleRefundedEvent` (inventory restoration) and never touched the cash shift. After a refund the shift still showed the full sale in `totalSales` / `cashSales` / `cardSales`, so **Cash Shift ≠ Sales** and the Z report overstated turnover.

**Documented deviation from the literal requirement:** the task listed `qrSales`, but the `CashShift` schema has **no `qrSales` column** (only `cashSales`, `cardSales`, `totalSales`). At completion, all non-cash methods (CARD, QR, …) are pooled into `cardSales`. The refund therefore mirrors the **exact allocation applied at completion**: cash → `cashSales` net of change, all non-cash → `cardSales`. This keeps `Cash Shift == Sales` exactly; a dedicated `qrSales` column would require a schema migration and is deferred to a future release (see §6 backlog).

### 3.2 `sales.service.ts` (`refundSale`)

```diff
     // NOTE: Inventory changes (stock restoration + stock movement) are handled
     // by the SaleRefundedEventHandler in the Inventory module via the EventBus.
     // This service ONLY publishes the event — it no longer directly mutates stock.

+    // Net the refunded amounts out of the linked cash shift, reversing the
+    // exact allocation applied at completion: cash sales are net of change
+    // (tendered − change), all non-cash methods (CARD/QR/…) are netted from
+    // cardSales, and totalSales is reduced by the sale total. Only an OPEN
+    // shift is touched — a closed shift's Z report is final. The write is
+    // guarded by rowVersion (optimistic locking): a stale version throws
+    // ConflictException and rolls the whole transaction back, so a refund can
+    // never be double-counted against a concurrently-mutated shift.
+    if (sale.cashShiftId) {
+      const shift = await tx.cashShift.findFirst({
+        where: { id: sale.cashShiftId, companyId },
+      });
+      if (shift && shift.status === 'OPEN') {
+        const payments = await tx.payment.findMany({
+          where: { saleId: sale.id },
+        });
+        let cashTotal = new Decimal(0);
+        let cardTotal = new Decimal(0);
+        for (const p of payments) {
+          if (p.method === 'CASH') cashTotal = cashTotal.add(p.amount);
+          else cardTotal = cardTotal.add(p.amount);
+        }
+        const changeAmount = new Decimal(sale.changeAmount.toString());
+        const cashSalesNet = cashTotal.sub(changeAmount);
+        const saleTotal = new Decimal(sale.total.toString());
+
+        await this.cashShiftRepository.update(
+          shift.id,
+          {
+            cashSales: new Decimal(shift.cashSales.toString()).sub(cashSalesNet),
+            cardSales: new Decimal(shift.cardSales.toString()).sub(cardTotal),
+            totalSales: new Decimal(shift.totalSales.toString()).sub(saleTotal),
+          },
+          companyId,
+          shift.rowVersion ?? 0,
+          tx,
+        );
+      }
+    }
+
     // Publish SaleRefundedEvent
```

**Why no double decrement:** `refundSale` runs only inside `transitionStatus(…, REFUNDED)`, `REFUNDED` is a terminal state in `VALID_TRANSITIONS`, and the shift write is guarded by optimistic locking inside the same transaction — a second refund attempt is rejected by the status-transition validation, and a concurrent shift mutation rolls back via `ConflictException`.

## 6. Remaining debt / backlog (not fixed, out of scope)

- **`qrSales` column**: schema has no QR-sales split on `CashShift`; QR is pooled into `cardSales` (same as completion). A migration to add `qrSales` (and split at completion + refund) is a clean v1.2 improvement if QR reporting granularity is needed.
- **Multi-adjustment journal reference**: two adjustments on the same product share `referenceId = productId` (pre-existing behavior; harmless, journals are distinct). A per-adjustment `referenceId` would improve traceability.
- **Expected closing** is computed at close (not on X report); X report shows the stored value. Intentional; matches closeShift calculation.
