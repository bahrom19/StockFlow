# StockFlow v1.2 — Phase 1: Payment Analytics Foundation

**Status:** Implemented & validated (local acceptance 52/52)
**Scope:** Explicit per-method payment accounting on the cash shift without touching GL, journal, costing, FIFO or average-cost engines.

---

## 1. Database (additive, backward compatible)

New `PaymentMethod` enum value:

```
MOBILE_WALLET   (added after BANK_TRANSFER; existing values unchanged)
```

New `CashShift` columns (all `DECIMAL(18,4) NOT NULL DEFAULT 0` — existing rows unchanged):

| Column | Meaning |
|---|---|
| `qrSales` | QR-payment sales total |
| `bankTransferSales` | Bank-transfer sales total |
| `mobileWalletSales` | Mobile-wallet sales total |

Migration: `20260805120000_add_payment_method_analytics` (purely additive — `ALTER TYPE ... ADD VALUE` + `ALTER TABLE ... ADD COLUMN` with defaults). Verified with `prisma validate` and applied to the local dev DB without reset; safe for `prisma migrate deploy` in production.

## 2. Payment allocation (explicit, fails fast)

New helper `backend/src/modules/sales/services/payment-allocation.ts`:

- `SHIFT_SALES_METHODS = ['CASH','CARD','QR','BANK_TRANSFER','MOBILE_WALLET']`
- `allocateShiftSales(payments)` → `{ cash, card, qr, bankTransfer, mobileWallet }`
- **Unknown methods (incl. legacy `GIFT_CARD`/`STORE_CREDIT`) throw `400 BadRequestException`** before any shift mutation — a sale can never silently land in the wrong bucket.

Previously non-cash payments were pooled into `cardSales`; now every method has its own bucket:

```
CASH           → cashSales
CARD           → cardSales
QR             → qrSales
BANK_TRANSFER  → bankTransferSales
MOBILE_WALLET  → mobileWalletSales
```

## 3. Refund allocation (exact composition reversal)

`refundSale` subtracts the **exact original allocation** from the linked OPEN cash shift — each method from its own bucket, cash still net of change, `totalSales` minus sale total. Example:

```
Sale:   Cash 1000 + Card 500 + QR 400 + Bank 200 + Wallet 300 = 2400
Refund: -1000      -500      -400      -200       -300       = 0
```

Optimistic locking (`rowVersion`) preserved; double-refund rejected by the terminal `REFUNDED` state; CLOSED shifts untouched (Z report final).

## 4. Reports

- **Cash Shift / X / Z reports** — every method exposed independently (`cashSales`, `cardSales`, `qrSales`, `bankTransferSales`, `mobileWalletSales`, `totalSales`).
- **Sales Report** `summary.payments` — `cash`, `card`, `qr`, `bankTransfer`, `mobileWallet`, `other` (legacy remainder).
- **Invariant:** `cash + card + qr + bankTransfer + mobileWallet == totalSales` (verified on X and Z reports).

## 5. Accounting (unchanged)

- GL Engine, Journal Engine, Costing, FIFO, Average Cost — **not modified**.
- `FinanceIntegrationService`: `MOBILE_WALLET` added to the same bank-receivable group as CARD/QR/BANK_TRANSFER (journal shape identical to v1.1.1 for all existing methods; MOBILE_WALLET now maps to the bank account instead of the "other" fallback).
- All v1.1.1 invariants preserved (see §7).

## 6. API / compatibility

- `CreatePaymentDto.method` / `SaleQueryDto.paymentMethod` / `PaymentEntity.method` enum lists extended with `MOBILE_WALLET` (additive).
- CashShift entity/mapper expose the 3 new fields (additive JSON keys — old clients ignore them).
- Existing endpoints, routes and response shapes otherwise unchanged.
