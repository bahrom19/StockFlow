# StockFlow v1.2 — Phase 2: Payment Analytics UI (Flutter)

**Status:** Implemented · Validated · GO

**Date:** 2026-08-05

## 1. Overview

Phase 2 delivers a complete Payment Analytics module in the Flutter client,
consuming **only** the existing production endpoints (`GET /reports/sales` and
`GET /sales`). No backend, API, schema or accounting changes were made.

The module surfaces the v1.2 per-method accounting (CASH / CARD / QR /
BANK_TRANSFER / MOBILE_WALLET) everywhere a cashier looks, and visually
enforces the invariant:

```
Cash + Card + QR + Bank Transfer + Mobile Wallet == Total Sales
```

## 2. Screens

### Screen 1 — Payment Analytics Dashboard (`/payments`)
- **Top cards** for each of the 5 methods: total amount, % of total revenue,
  transaction count, average ticket. Tapping a card deep-links into
  Payment Details pre-filtered for that method and period.
- **Payment Distribution** — animated pie chart with % labels + legend.
- **Daily Trend** — multi-series line chart (one line per method), with a
  selectable period: **Today / Week / Month / Custom** (date-range picker).
- **Payment Comparison** — animated bar chart toggled between **Amount /
  Transactions / Average Ticket**.
- Loading (skeleton), empty and error states; a warning banner is rendered
  whenever `methodsSum != totalRevenue` (self-auditing UI).

### Screen 2 — Payment Details (`/payments/details`)
Desktop `EntityTable` with columns Date · Receipt · Cashier · Customer ·
Warehouse · Method · Amount · Status.
- Search (debounced 350 ms), method filter chips, sortable columns,
  pagination ("Load more") and CSV export.
- Method cells are color-coded with the v1.2 brand colors; refund statuses
  are highlighted. Rows deep-link to the sale detail screen.

### Cash Shift / X Report / Z Report (updated)
- Cash Shift strip and the X/Z report dialog + PDF now show all five buckets
  and display a warning when the breakdown differs from total sales.
- POS receipt PDF includes the same per-method rows.

### Dashboard — "Today's Payments" widget
Stacked distribution bar + per-method %/amount rows and a total. One request
(`GET /reports/sales` for today). Tapping opens the analytics screen.

## 3. Navigation

- `RouteNames.payments = '/payments'` and `paymentDetails = '/payments/details'`
  registered in the GoRouter (inside the auth shell).
- Sidebar: **INSIGHTS → Reports, Payments, Finance**.
- Deep-links: `context.push('/payments/details?method=CASH&from=...&to=...')`.

## 4. Architecture & Data Flow

```
Dashboard Today's Payments  ─┐
                             ├─ paymentsRepositoryProvider ── GET /reports/sales (summary.payments)
PaymentAnalyticsScreen       ─┤                                  GET /sales (per-day, per-method trend + counts)
PaymentDetailsScreen         ─┘
```

- **Domain:** `payment_models.dart` — `PaymentPeriod`, `PaymentMethodStat`,
  `PaymentDayPoint`, `PaymentAnalyticsData` (with `methodsSum`/`invariantOk`),
  `PaymentMethodMeta` (labels/colors/icons).
- **Data:** `payments_repository.dart` — `getSalesReport`, `getSalesForTrend`
  (paginated, capped), `getSalesPage`. Result wrapper mirrors the app pattern.
- **State:** `payment_analytics_provider.dart` — `StateNotifier` with period
  selection; **two parallel requests per load** (report + trend). Counts and
  the daily trend are derived from the same sale-list fetch (no 7-request fan-out).
  A generation counter discards stale responses on rapid period switches.
- **Dashboard card:** `today_payments_provider.dart` — lightweight
  `FutureProvider.autoDispose`, one request.

### Netting correctness (trend chart)
The daily trend nets each sale's `changeAmount` from its CASH contribution
(floored at zero), mirroring the v1.2.0 report fix — so an overpayment sale
(900 total / 1800 tendered / 900 change) shows **900** cash in the line chart,
consistent with the pie and top cards.

## 5. Performance

- **Requests per screen load:** analytics = 2 (report + sale list); details = 1
  per page; dashboard card = 1.
- **Debounced search** (350 ms) on Payment Details with a request-sequence
  guard preventing out-of-order responses.
- **No N+1:** sale list is fetched once and drives both counts and the trend.
- Charts render with `fl_chart 0.69.0` (pinned — 0.71+ requires a newer Flutter
  SDK than the project's 3.24.5 and was rejected by dart2js).
- The trend fetch is capped at 25 pages (2,500 sales) — documented limitation
  for very high-volume periods (see §8).

## 6. Responsive & Dark Mode

- Cards: 5-across (wide) / 3 (tablet) / 2 (mobile) via `LayoutBuilder`.
- Charts stack vertically below the desktop breakpoint.
- All colors derive from `Theme.of(context)` / `PaymentMethodMeta` brand colors,
  so dark mode is fully supported.

## 8. Known Limitations

1. **Trend cap:** the daily-trend source stops after 25 pages (2,500 sales).
   Beyond that, the chart is truncated (top cards remain exact — they come
   from the report summary).
2. **Counts from the sale list:** per-method transaction counts come from the
   same capped fetch; for stores exceeding 2,500 sales/period the counts could
   under-report. Exact totals always come from the report summary.
3. **Export placeholder:** CSV export is live (via `CsvExporter`); PDF export
   of Payment Details was left as the documented next step (ReceiptPrintService
   reuse).
4. **`other` pool:** legacy GIFT_CARD / STORE_CREDIT payments still pool into
   `other` — out of scope (Phase 2 backlog).
